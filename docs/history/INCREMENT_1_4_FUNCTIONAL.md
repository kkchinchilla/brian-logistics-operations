### 核心安全條件

- 只有主管可在每日出勤頁新增或更動預排；司機只能提交自己已分派趟次的實際變更。
- 已結案日期禁止修改預排。`sql/140_01_closed_day_run_guard.sql` 新增 DB trigger，覆蓋 `runs` 的 INSERT/UPDATE/DELETE；同時避免回頭更改 **已確認配送** 的主關聯資料。
- 路線主檔已有的固定溫層、固定起迄時間及 DB 時間衝突檢查沿用舊規則。前端不自行更改派車時間或薪資計價。
- 月報不得用「是否綁定自有車」推測租車；僅計入實際執行紀錄的明確 `is_rental === true`，未確認另列。
- 保留原本的 `js/config.js`，且 ZIP **不含**真實 Supabase 連線設定。
- 不會匯入任何展示資料，也沒有刪除、重建或自動改寫歷史營運紀錄。

## 增量安裝（推薦）

1. 先備份目前可正常登入的 `dispatch-system-v0.5.5` 整個目錄，並確認 Supabase 資料庫可復原。
2. 解壓 `dispatch-increment-1.4-functional-patch.zip` 到 `dispatch-system-v0.5.5` 的**上一層**並合併覆蓋同名檔案。CSS、Prototype、路線管理檔案均不更動。
3. 在 Supabase SQL Editor 先檢查 `sql/132_01_shared_dashboard.sql` 已安裝，再執行 **`sql/140_01_closed_day_run_guard.sql`**；接著執行只讀檢查 `sql/140_02_verify_readonly.sql`。
4. 用既有主管帳號登入，驗證以下流程。請優先使用**專門的測試日期、非營運測試車輛／司機／路線**。
5. 若使用完整包 `dispatch-system-increment-1.4-full-no-config.zip`，另外保留原本的 `js/config.js`。不需要重新執行 131、132 的 SQL。
6. 強制重新整理快取 macOS `⌘ + Shift + R` / Windows `Ctrl + Shift + R`。

> 即使不執行 140 SQL，UI 可能顯示新增功能；但資料庫不會可靠地阻止其他舊版頁面修改已結案日期。**正式環境請務必完成 140 SQL。**

## 上線前手動驗收

1. 每日出勤：新日期新增 1 趟，選擇路線／司機／車輛／是否租車，存檔後刷新應保留；同一溫層 5 趟以上仍展開正確欄數。再用主管打開既有預排，更新後刷新。
2. 驗證原有重疊班次被資料庫拒絕，並且未選租車狀態不可提交。
3. 把**測試日期**結案：新增按鈕不可用；從舊版 `dispatcher.html` 修改該日預排也應被 140 SQL trigger 拒絕；重新開啟後可修改。
4. 已確認完成的測試趟次不得重新歸屬到其他司機、路線或車輛。
5. 車輛管理：開啟某車的綁定歷史，設定結束日、新增下一個不重疊的綁定。重疊日期應拒絕而不改寫舊紀錄。
6. 月報：選擇有真實已確認趟次的月份；檢查 `is_rental=true` 被計入租車，`is_rental=NULL` 顯示未確認而不計入。匯出 CSV 與畫面一致。
7. 司機帳號測試：能讀取共用出勤表，不可新增或修改他人的預排。
8. 手機檢查出勤表、綁定對話框及月報矩陣橫向捲動；路線管理 sidebar CSS 應維持與前版一致。
