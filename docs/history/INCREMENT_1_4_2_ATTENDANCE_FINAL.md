# Increment 1.4.2 — 每日出勤「實際路線 / 臨時趟次 / 多人編輯」

基礎版本：已通過驗收的 **Increment 1.4.1**。保留四個 Dashboard 的共用外觀；只更動 `ui-attendance.html`、`js/production-attendance.js`、新增 `css/attendance-actual-142.css`，並加上 SQL、測試與本文件。

## 新功能

1. **實際路線與車號**：點擊已有預排的儲存格，可分別選擇實際配送路線、實際車輛與備註。原定 `runs.route_id` / `runs.vehicle_id` 不變；差異存於 `daily_run_observations.actual_route_id` / `actual_vehicle_id`，黃底標示真正與原定不同的欄位。取消不寫入。恢復「依原定」可取消覆寫。已被核對確認的 `trip_executions.review_status='confirmed'` 禁止直接覆寫實際紀錄，需另走正式更正流程。
2. **臨時／未預排的實際趟次**：出勤表空白欄位出現小型「＋」。主管可編輯全公司、司機只能編輯自己的空白欄位。輸入實際路線、車輛、是否租車、備註，透過 RPC 儲存至獨立 `daily_attendance_extra_trips`（不覆寫 `runs`）。可撤銷（必填原因）並再次建立，透過 `status='void'`、`revision` 及 `daily_attendance_change_log` 留存歷史，不實體刪除。
3. **欄位保護**：臨時趟次不能佔用已有預排的欄位；預排趟次也不能佔用已有臨時趟次的欄位。已佔用臨時趟次的最後欄位不能使用「調整趟數」隱藏。以與 1.4.1 相同日期 advisory lock 避免兩位操作者同時衝突。
4. **併發控制**：實際紀錄、臨時紀錄用 `revision` 樂觀鎖；預排 `runs` 新增 `dashboard_schedule_revision`，修改預排時先比對版本。衝突時顯示重新載入／重新編輯，不默默覆寫。撤銷和恢復同樣驗證版本。
5. **結案保護**：出勤實際紀錄與臨時趟次在結案後不能改動；結案寫入也套同一天的交易鎖，避免當日結案和同時保存發生競態。司機只能寫自己的實際資料（SQL 層驗證）。
6. **新增記錄追蹤**：新增的 observation／extra 變更都在 `daily_attendance_change_log` 留痕，可供主管稽核。實際界面尚無獨立稽核歷程頁面，SQL 層已保存。

## 不包含 / 需後續系統整合

- **臨時實際趟次不會自動建立 `runs` 或 `trip_executions`，亦不會自動產生工資或已確認趟次。** 目前月度報表只計既有核對完成的 `trip_executions`；`daily_attendance_extra_trips` 暫時不進入薪資數字，避免未核價的臨時紀錄直接增加薪資。月報增量需定義主管核可、路線費率及與結算的對應規則。
- SQL 保護的是既有預排與出勤欄位、身份權限、日期鎖及版本衝突；**跨多趟「實際車輛」衝突**尚未按實際出發／返回時刻檢查（現行實際趟次沒有實際時刻欄位），不可把它視為已完成該時間衝突規則。
- 本包不導入展示資料、不重算或改寫既有薪資、不變更路線主檔／車輛管理／月報 Dashboard 的 HTML、CSS 或 JS。

## 安裝步驟

1. 先備份已驗收的 Increment 1.4.1 程式與 Supabase DB，確認復原方式。以下操作先於 **測試 Supabase 專案** 執行。
2. 在 SQL Editor 執行 `sql/142_01_actual_trip_workflows.sql`，它依賴 132／140／141 已成功安裝。接著執行 `sql/142_02_verify_readonly.sql`，確認函式、欄位、RLS、觸發器都存在。SQL **不刪除、重設或自動分類舊的出勤資料**。
3. 解壓增量包到 `dispatch-system-v0.5.5` 的**上一層**，合併覆蓋同名檔案；保留既有 `js/config.js`。用瀏覽器強制重整頁面。**建議先安裝 SQL，再換前端**，避免新版欄位讀取在資料庫尚未升級時處於安全降級狀態。
4. 在測試專案實際用主管及司機兩種角色測試，確認後再於正式 Supabase 專案備份、部署 SQL 與前端。
5. 本次 SQL 將 `daily_run_observations` 的直接 INSERT/UPDATE 權限改為 RPC 寫入（避免跳過版本檢查）。舊版 1.4.1 的瀏覽器頁面若仍快取，不再能直接保存該表；更新前請讓操作人員停止編輯並重新整理。

## 使用正式角色與 Supabase 的必要驗收

- [ ] 主管：原定路線 AA / 車號 01，修改實際路線 BB／車號 02，儲存／重整後黃底顯示，原定 `runs` 不被覆寫；恢復依原定兩欄，黃底消失。
- [ ] 司機 A 可看全公司但只能點擊自己的實際儲存格與空白格；不可修改司機 B，也不可新增／調整預排、調整每日欄數、結案。主管可編輯任一司機。
- [ ] 空白的冷凍2 建立臨時配送，填路線／車號／租車選項；顯示於原儲存格，刷新後保留，沒有建立新的 `runs`。撤銷時必填原因，儲存格恢復可新增，稽核紀錄仍在。
- [ ] 臨時配送佔用冷凍5 時，禁止從 5 欄縮回 4；主管也不能把預排放入同一司機同一天同類同序號。兩位操作人員同時建立相同臨時配送，只能有一位成功。
- [ ] 兩個瀏覽器同時編輯同一個實際趟次，後存的一方應顯示「資料已被其他人更新」；預排編輯亦同。刷新後看到先保存的修改。
- [ ] 在儲存臨時趟次／實際改線的同時由主管結案，不能產生結案後未被檢查的寫入。結案後不可編輯；重新開啟後可再編輯。
- [ ] 已有 confirmed `trip_executions` 的原定趟次不能直接用實際變更 RPC 更動；需更正流程。
- [ ] 檢查 `daily_attendance_change_log` 追蹤到操作者、時間、舊／新內容；一般司機不得查看完整主管稽核表。
- [ ] 月報數字不因新增臨時配送而自動增加或擅自核價；現有 4 Dashboard 資料正常載入。
- [ ] 手機 320/375、平板 768、桌機 1366 寬度內容不越界；Chrome/行動 Safari 實機再驗收一次。
